# Архитектура

Документ описывает текущее устройство приложения «Контент-план». Последняя сверка с кодом: 18 августа 2026 года.

## Общая схема

Приложение состоит из одностраничного статического клиента и серверных событийных функций Firebase.

```text
Браузер
  ├── index.html — точка входа
  ├── 404.html — автономная страница для несуществующих адресов
  ├── assets/ — продуктовые снимки публичного лендинга
  ├── styles.css — визуальное оформление
  └── app.js — рендеринг экранов и бизнес-логика
         │
         ├── Firebase Authentication — пользователи и сессии
         └── Cloud Firestore — проекты, планы, изображения, комментарии, история и доступ
                  │
                  └── Cloud Functions — неизменяемый журнал действий с auth context
```

`app.js` загружает Firebase JavaScript SDK 12.0.0 как ES-модули с CDN `gstatic.com`. HTML для экранов формируется шаблонными строками и помещается в `<main id="app">`. Отдельного роутера, фреймворка, сборки и локального HTTP API нет. Каталог `functions/` использует Node.js 22, Firebase Admin SDK и Cloud Functions for Firebase второго поколения. Страница `404.html` не загружает `app.js` и Firebase: она использует общие стили, автономную SVG-иллюстрацию и CSS-анимации.

## Состояние и навигация

Глобальное состояние в памяти вкладки:

- `user` — текущий пользователь Firebase Authentication;
- `projects` — доступные пользователю проекты вместе с его ролью;
- `planZoom` — масштаб сетки плана, от 80% до 140%;
- `planOffset` — смещение отображаемого календарного месяца.

После изменения состояния экраны перерисовываются целиком. Между сессиями масштаб и смещение не сохраняются.

Основной экран выбирается при изменении состояния авторизации:

1. Неавторизованный пользователь видит публичный лендинг. Кнопки на нём открывают вход или регистрацию внутри того же SPA; кнопка «Назад» возвращает на лендинг.
2. Авторизованный пользователь без специальных query-параметров видит список проектов, однострочное персональное приветствие и визуально вынесенную на передний план SVG-анимацию оливки. При `prefers-reduced-motion: reduce` персонаж остаётся статичным. Выбор проекта открывает промежуточный проектный хаб `renderProjectWorkspace`.
3. Адрес с `?plan=<projectId>&network=<networkId>` открывает контент-план конкретной площадки.
4. Адрес с `?mode=verifyEmail&oobCode=<code>` открывает собственный обработчик подтверждения email независимо от текущей сессии.

Проектный хаб показывает пять направлений: «Соцсети», «Целевая аудитория», «Конкуренты», «Аудит» и «Референсы». В текущей версии только «Соцсети» является активной кнопкой и ведёт на существующий экран выбора площадки; остальные направления отображаются отключёнными со статусом «Скоро» и не выполняют запросов к Firestore. Назад с экрана соцсетей пользователь возвращается в проектный хаб, а из хаба — к списку проектов.

На экране выбора соцсети кнопка «История» открывает последние 100 серверных событий проекта. Экран доступен владельцу, редактору и читателю и загружается по запросу без real-time подписки.

На экране выбора соцсети владелец и редактор назначают ответственного из участников проекта; читатель видит сохранённое имя. Выбор соцсети открывает план в новой вкладке. Кнопка «Закрыть вкладку» вызывает `window.close()`, что гарантированно работает только для вкладок, открытых скриптом.

Публичный лендинг рендерится функцией `renderLanding`. Якорные ссылки прокручивают страницу к возможностям, рабочему процессу и ролям. Галерея продукта переключает локальные снимки фактических экранов из `assets/`: главная и редактор публикации соответствуют текущему интерфейсу приложения. Функция `landingOllieMarkup` формирует единую SVG-модель Олли для приветствия, выглядывания из окна и бега с блокнотом. Появление блоков и персонажи анимированы CSS и `IntersectionObserver`; при `prefers-reduced-motion: reduce` контент сразу видим, а движение отключается.

Несуществующий адрес обрабатывается статическим хостингом через `404.html`. Кнопка «Попробовать еще раз» ведёт на корень сайта. При системной настройке `prefers-reduced-motion: reduce` декоративные анимации отключаются, а вторая оливка остаётся видимой внутри нуля.

## Основные пользовательские сценарии

### Регистрация и вход

Регистрация создаёт пользователя Firebase Authentication, обновляет его `displayName`, записывает профиль в `profiles/{uid}` и отправляет письмо через `sendEmailVerification`. Сессией управляет Firebase Authentication через `onAuthStateChanged`. Пока `emailVerified` имеет значение `false`, приложение показывает отдельный экран подтверждения с повторной отправкой письма и не загружает проекты.

Action URL шаблона Firebase указывает на корень приложения. При открытии письма приложение распознаёт `mode=verifyEmail`, проверяет `oobCode` через `checkActionCode`, а после нажатия кнопки применяет его через `applyActionCode`. Оно показывает собственные состояния проверки, успеха и недействительной ссылки; параметры действия удаляются из адресной строки после успеха. Если в браузере есть активная сессия, пользователь и его ID-токен обновляются перед возвратом к проектам, чтобы правило `email_verified` стало доступно Firestore. Декоративные CSS-анимации оливок отключаются при `prefers-reduced-motion: reduce`.

### Создание проекта

Мастер состоит из двух экранов. На первом пользователь вводит название и описание. На втором он вручную добавляет соцсети, затем создаёт рубрики и связывает каждую рубрику с одной или несколькими добавленными соцсетями. До финального подтверждения черновик хранится только в памяти вкладки.

После нажатия «Создать проект» выполняются последовательные операции:

1. создаётся документ проекта;
2. создаётся membership владельца;
3. создаётся активное приглашение с уникальным восьмизначным кодом;
4. создаются добавленные соцсети;
5. создаются рубрики с идентификаторами связанных соцсетей;
6. открывается проектный хаб созданного проекта, из которого доступен экран выбора соцсети.

Эти операции не объединены в транзакцию или batch. При сетевой ошибке возможен частично созданный проект.

### Присоединение по коду

Пользователь читает `invitations/{code}` и создаёт membership с ролью `viewer`. Владелец проекта затем может указать свободным текстом функцию участника, изменить его роль на `editor` или удалить участника, удалив его membership. Роль владельца удалить через экран доступа нельзя. Владелец и редактор могут читать список memberships, чтобы выбирать ответственных; читатель получает только собственный membership и видит сохранённые в соцсети и публикации снимки имён. Менять функцию, права и состав команды может только владелец.

Устаревшая роль `commenter` больше не назначается и на клиенте имеет права читателя. Когда владелец открывает экран доступа, все memberships с этой ролью пакетно переводятся в `viewer`. До такой миграции правила Firestore сохраняют для `commenter` только чтение, чтобы участники не потеряли доступ внезапно.

### Контент-план

Для выбранной площадки загружаются проект, membership пользователя, площадка, все рубрики проекта и все публикации проекта. На клиенте остаются только рубрики и публикации выбранной площадки.

Сетка показывает все дни выбранного месяца и ровно столько колонок, сколько рубрик назначено площадке. Существующая публикация доступна всем участникам на чтение; пустую ячейку может открыть только владелец или редактор.

У рубрик, созданных ранней версией приложения, может отсутствовать `networkIds`. Для обратной совместимости клиент считает такую рубрику общей для всех существующих соцсетей проекта; при следующем сохранении редактора записывается явный массив идентификаторов. Редактор проверяет название, выбор хотя бы одной соцсети и отсутствие повторяющихся названий до начала запросов. На время последовательных операций форма блокирует повторную отправку и показывает прогресс, поэтому один пользовательский клик не может создать несколько одинаковых документов.

### Публикации и комментарии

Владелец и редактор создают, изменяют и удаляют публикации. В новой публикации ответственным по умолчанию выбран ответственный за соцсеть; пользователь может назначить другого участника или оставить публикацию без исполнителя. Выбор сохраняется в публикации отдельно и не меняется при последующей смене ответственного соцсети. Перед сохранением браузер уменьшает изображения до 1400 пикселей по большей стороне, кодирует их в WebP и доводит размер примерно до 90 КБ. До четырёх изображений публикации сохраняются отдельными документами `postImages`, чтобы не приближать основной документ публикации к лимиту Firestore. Нажатие на превью открывает изображение во вложенном модальном просмотрщике без перехода на Data URL в новой вкладке. Комментарии к сохранённым публикациям могут добавлять владелец и редактор. Читатель видит данные без возможности изменения.

### История действий

Семь Firestore-триггеров с auth context отслеживают создание, изменение и удаление проекта, площадок, рубрик, публикаций, изображений, комментариев и memberships. Обработчик получает UID пользователя из доверенного контекста события, читает снимок имени из профиля и записывает краткое событие в `projects/{projectId}/activity/{eventHash}`. Хеш идентификатора исходного CloudEvent делает повторную доставку события идемпотентной. Клиентским правилам запрещено создавать и изменять записи истории.

История хранит тип операции, сущность, список изменённых полей, читаемое описание, автора и серверное время события. Полные версии текстов публикаций не сохраняются, поэтому журнал предназначен для аудита действий, а не для восстановления содержимого. События, произошедшие до первого развёртывания функций, задним числом не создаются. Доставка Firestore-триггеров асинхронная, поэтому новая запись может появиться с небольшой задержкой.

### Удаление проекта

Перед удалением клиент ставит в проекте временную метку `deletingAt`, чтобы серверные триггеры не создавали новые события во время очистки. Затем проверяется доступ владельца ко всем подколлекциям и удаляются площадки, рубрики, публикации, изображения, комментарии и история, после них — участники, приглашение, проект и membership владельца. Если удаление останавливается до удаления проекта, клиент старается снять `deletingAt`, чтобы аудит последующих действий продолжился. Операция по-прежнему не является серверной транзакцией. Правила и функции должны публиковаться отдельно от статического сайта.

## Границы ответственности файлов

| Файл | Ответственность |
| --- | --- |
| `index.html` | метаданные страницы, корневой DOM-элемент, подключение стилей и модуля |
| `favicon.svg` | векторный логотип `CP` для вкладки браузера |
| `assets/` | локальные PNG-снимки фактических экранов продукта для лендинга |
| `styles.css` | семантические переменные природной палитры, публичный лендинг, компоненты приложения, сетки, модальные окна и адаптивность |
| `app.js` | Firebase-конфигурация, запросы к данным, проверки ролей, лендинг и рендеринг экранов приложения |
| `firestore.rules` | обязательная серверная авторизация операций с Firestore |
| `firebase.json` | точки входа Firebase CLI для правил и функций |
| `functions/index.js` | серверное формирование идемпотентных записей истории |

Проверки `canEdit` и `canComment` в интерфейсе нужны для удобства, но не являются защитой. Источник истины для разрешений, включая доступ к изображениям, — опубликованные правила Firestore.

## Внешние зависимости

- Firebase Authentication с включённым провайдером Email/Password;
- Cloud Firestore;
- Cloud Functions for Firebase второго поколения и тариф Blaze;
- Node.js 22 и Firebase CLI для установки зависимостей и развёртывания функций;
- Firebase JavaScript SDK 12.0.0 с CDN;
- статический хостинг с HTTPS для production;
- современный браузер с ES-модулями, `Intl.DateTimeFormat`, Clipboard API, File API, Canvas API, `createImageBitmap` и `window.open`.

## Известные технические риски

- запросы к `memberships` по `userId` и `projectId` могут потребовать индексов по мере усложнения фильтров;
- нет транзакций для составных операций создания и удаления проекта;
- удаление площадок и рубрик не проверяет связанные документы;
- фильтрация публикаций по площадке выполняется на клиенте;
- нет real-time обновлений: изменения других участников видны только после повторной загрузки экрана;
- история ограничена последними 100 событиями в интерфейсе и не является хранилищем версий;
- вся логика сосредоточена в одном модуле, поэтому дальнейший рост усложнит сопровождение.

При устранении любого из этих ограничений обновите этот документ, модель данных и README, если меняется пользовательское поведение.
