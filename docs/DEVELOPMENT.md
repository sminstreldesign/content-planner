# Разработка и выпуск изменений

## Требования

- современный браузер;
- доступ к Firebase-проекту для настройки Authentication и Firestore;
- любой локальный статический HTTP-сервер;
- Git для работы с репозиторием.

Установка JavaScript-зависимостей не требуется: Firebase SDK загружается с CDN.

## Локальный запуск

Из корня репозитория:

```powershell
python -m http.server 8000
```

Откройте `http://localhost:8000`. Если Firebase отклоняет вход, проверьте, что `localhost` добавлен в Authorized domains. Не запускайте приложение через `file://`, поскольку браузерные ограничения ES-модулей отличаются от production-окружения.

Страницу ошибки можно проверить напрямую по адресу `http://localhost:8000/404.html`. На production-хостинге настройте этот файл как документ для HTTP 404, если платформа не подхватывает `404.html` автоматически.

## Настройка Firebase

Для нового окружения:

1. Создайте или выберите Firebase-проект.
2. Добавьте Web App и перенесите значения в `firebaseConfig` в начале `app.js`.
3. Включите **Authentication → Sign-in method → Email/Password**.
4. В **Authentication → Templates** проверьте шаблон письма подтверждения email и адрес отправителя.
5. Создайте Cloud Firestore.
6. Опубликуйте содержимое `firestore.rules`: доступ к данным требует подтверждённый email.
7. Добавьте домены локального и production-хостинга в Authorized domains.

Не ослабляйте Firestore rules ради исправления интерфейсной ошибки. Сначала сопоставьте требуемое действие с матрицей ролей в `DATA_MODEL.md`.

## Принципы внесения изменений

- Экраны рендерятся функциями `render*`; модальные сценарии открываются через `openModal`.
- Пользовательские значения, вставляемые в HTML, должны проходить через `esc`.
- Даты публикаций хранятся строкой `YYYY-MM-DD`; для отображения используется локаль `ru-RU`.
- Серверное время записывается через `serverTimestamp()`.
- Видимость кнопок должна соответствовать Firestore rules, но не заменять их.
- Новая операция над данными должна быть разрешена или явно запрещена в `firestore.rules`.
- При добавлении поля задокументируйте его назначение, тип и жизненный цикл в `DATA_MODEL.md`.

## Проверка перед завершением изменения

Автоматических тестов пока нет, поэтому минимальная проверка выполняется вручную.

### Статическая проверка

Если установлен Node.js:

```powershell
node --check app.js
```

Также проверьте `git diff --check`, чтобы найти ошибки пробелов и конфликтные маркеры.

### Дымовой сценарий

1. Открыть сайт без сессии, зарегистрироваться, проверить отправку письма, экран ожидания, повторную отправку и запрет доступа к проектам до подтверждения email. Перейти по ссылке, нажать «Я подтвердил(а) email» и проверить вход. Для уже подтверждённого аккаунта проверить обычный повторный вход.
2. Создать проект через два шага: заполнить название и описание, вручную добавить хотя бы одну площадку, создать рубрику и связать её с площадкой. Проверить возврат на первый шаг без потери черновика.
3. Открыть план, проверить количество дней выбранного месяца и соответствие колонок рубрикам, затем создать, изменить и удалить публикацию.
4. Загрузить до четырёх изображений в поля «Референсы и скрины» и «Визуал», сохранить публикацию и проверить сжатые превью, встроенный просмотр по клику, закрытие просмотрщика по крестику и Escape, удаление изображения и цвет статуса в сетке.
5. Добавить комментарий к сохранённой публикации.
6. Присоединить второго пользователя по коду.
7. Проверить интерфейс и фактические разрешения для `viewer` и `editor`. Если есть тестовый membership с устаревшей ролью `commenter`, открыть экран доступа владельцем и проверить его автоматический перевод в `viewer`.
8. Владелец меняет роль второго пользователя, затем удаляет его на экране доступа. Проверить исчезновение участника из списка, запрет последующих операций с его открытой вкладки и отсутствие проекта после повторной загрузки этой вкладки. Убедиться, что удалить владельца через интерфейс нельзя.
9. Изменить название, площадки и рубрики проекта. Для рубрики без выбранной соцсети проверить цветную подсветку строки и перевод фокуса к ошибке. Быстро нажать сохранение несколько раз и убедиться, что создаётся только один документ, кнопка блокируется, а прогресс исчезает после ответа. Отдельно открыть старую рубрику без `networkIds`, проверить автоматический выбор существующих соцсетей и сохранение явной привязки.
10. С опубликованной актуальной версией `firestore.rules` проверить удаление тестового проекта владельцем и отсутствие связанных документов и изображений.
11. Проверить узкий экран и отсутствие критического горизонтального переполнения вне таблицы плана.
12. Открыть `404.html` на широком и узком экране: проверить жест 6–7 у грустной оливки, появление второй оливки внутри нуля, движение её рук и ног, переход кнопки на корень сайта и статичное доступное состояние при `prefers-reduced-motion: reduce`.

Для небольших визуальных изменений достаточно релевантной части сценария. Изменения модели данных или правил требуют проверки минимум с владельцем и одной затронутой ролью.

## Обновление документации

Документация является частью готовности изменения. Перед завершением работы ответьте на вопросы:

- Изменилось пользовательское поведение или список возможностей? Обновите `README.md`.
- Изменилась навигация, интеграция или ответственность модулей? Обновите `ARCHITECTURE.md`.
- Изменились коллекции, поля, статусы, роли или Firestore rules? Обновите `DATA_MODEL.md`.
- Изменились запуск, проверка или выпуск? Обновите `DEVELOPMENT.md`.
- Появилось новое известное ограничение или устранено старое? Обновите README и соответствующий технический документ.

Если обновление не требуется, это должно быть осознанным выводом после проверки этих пунктов.

## Выпуск

1. Выполните релевантный дымовой сценарий.
2. Убедитесь, что документация соответствует изменению.
3. Опубликуйте новую версию Firestore rules, если файл менялся.
4. Опубликуйте статические файлы на хостинге.
5. Проверьте production-домен, авторизацию и один основной сценарий после публикации.

Изменение `firestore.rules` в репозитории само по себе не обновляет правила в Firebase Console.
