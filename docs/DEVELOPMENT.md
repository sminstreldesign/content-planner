# Разработка и выпуск изменений

## Требования

- современный браузер;
- доступ к Firebase-проекту для настройки Authentication и Firestore;
- любой локальный статический HTTP-сервер;
- Git для работы с репозиторием.
- Node.js 22 и npm для серверных функций;
- Firebase CLI для локальной проверки и развёртывания функций и правил.

Установка JavaScript-зависимостей не требуется: Firebase SDK загружается с CDN.

## Локальный запуск

Из корня репозитория:

```powershell
python -m http.server 8000
```

Откройте `http://localhost:8000`. Если Firebase отклоняет вход, проверьте, что `localhost` добавлен в Authorized domains. Не запускайте приложение через `file://`, поскольку браузерные ограничения ES-модулей отличаются от production-окружения.

Страницу ошибки можно проверить напрямую по адресу `http://localhost:8000/404.html`. На production-хостинге настройте этот файл как документ для HTTP 404, если платформа не подхватывает `404.html` автоматически.

## Настройка Firebase

Для нового окружения:

1. Создайте или выберите Firebase-проект.
2. Добавьте Web App и перенесите значения в `firebaseConfig` в начале `app.js`.
3. Включите **Authentication → Sign-in method → Email/Password**.
4. Создайте Cloud Firestore.
5. Опубликуйте содержимое `firestore.rules`: доступ требует действующую сессию, membership и подходящую роль, но не подтверждённый email.
6. Для истории действий подключите к проекту биллинг Blaze и настройте бюджетные уведомления.
7. Выполните `npm --prefix functions install`, затем опубликуйте функции и правила командой `firebase deploy --only functions,firestore:rules --project <project-id>`.
8. Добавьте домены локального и production-хостинга в Authorized domains.

Не ослабляйте Firestore rules ради исправления интерфейсной ошибки. Сначала сопоставьте требуемое действие с матрицей ролей в `DATA_MODEL.md`.

## Принципы внесения изменений

- Экраны рендерятся функциями `render*`; модальные сценарии открываются через `openModal`.
- Пользовательские значения, вставляемые в HTML, должны проходить через `esc`.
- Даты публикаций хранятся строкой `YYYY-MM-DD`; для отображения используется локаль `ru-RU`.
- Серверное время записывается через `serverTimestamp()`.
- Видимость кнопок должна соответствовать Firestore rules, но не заменять их.
- Новая операция над данными должна быть разрешена или явно запрещена в `firestore.rules`.
- При добавлении поля задокументируйте его назначение, тип и жизненный цикл в `DATA_MODEL.md`.

## Проверка перед завершением изменения

Автоматических тестов пока нет, поэтому минимальная проверка выполняется вручную.

### Статическая проверка

Если установлен Node.js:

```powershell
node --check app.js
node --check functions/index.js
```

Также проверьте `git diff --check`, чтобы найти ошибки пробелов и конфликтные маркеры.

### Дымовой сценарий

1. Открыть сайт без сессии на широком и узком экране. Проверить публичный лендинг, загрузку четырёх продуктовых снимков, соответствие главной страницы и редактора публикации фактическому интерфейсу, нейтральное приветствие «Здравствуйте!» без персонального имени на снимке главного экрана, Олли в приветствии, окне проекта и командной секции, единую палитру карточек возможностей, якорную навигацию, переключение вкладок «Настройка», «Публикация» и «План», раскрытие ответов, отсутствие горизонтального переполнения, кнопки входа и регистрации, возврат на лендинг и статичное доступное состояние при `prefers-reduced-motion: reduce`.
2. Зарегистрироваться и убедиться, что приложение без письма и промежуточного экрана сразу открывает список проектов. Выйти и повторно войти теми же email и паролем. Проверить анимированную оливку на главном экране в настольной и мобильной ширине; при `prefers-reduced-motion: reduce` она должна оставаться статичной.
3. Создать проект через два шага: заполнить название и описание, вручную добавить хотя бы одну площадку, создать рубрику и связать её с площадкой. Проверить возврат на первый шаг без потери черновика. После создания должен открыться проектный хаб «Над чем поработаем?».
4. На проектном хабе проверить широкую и узкую компоновку, возврат к списку проектов и рабочие переходы во все шесть разделов. В «Референсах» проверить отдельный столбец для каждой соцсети и горизонтальную прокрутку на узком экране. Владельцем создать и раскрыть карточку, добавить текст «что понравилось» и четыре изображения, проверить сжатие, превью, просмотр, ограничение пятого файла, замену набора вложений и удаление карточки. Повторить чтение карточки ролью `viewer` без элементов редактирования и изменение ролью `editor`. В анализе ЦА переименовать стартовые сегменты, добавить и удалить сегмент, добавить собственный критерий и группу, заполнить несколько ячеек, сохранить и повторно загрузить. Проверить ограничения, валидацию повторяющихся названий, внутреннюю горизонтальную прокрутку матрицы, редактирование владельцем и редактором и режим чтения для читателя. В анализе конкурентов переименовать свою компанию, добавить и удалить конкурента, вручную заполнить минимум три критерия, заметки и оценки 0–5. Проверить живое обновление радиальной диаграммы, сохранение и повторную загрузку. Редактор должен менять анализ, а читатель — видеть таблицу и диаграмму без элементов редактирования. На узком экране обе матрицы и диаграмма должны прокручиваться внутри карточек без переполнения всей страницы.
5. В «Аудите» и «Блокноте» добавить, переименовать, переключить и удалить главу. Для выделенного текста проверить все десять шрифтов, несколько размеров, уровни заголовков, начертания, списки и все двадцать цветов. Сохранить документ, повторно открыть его владельцем и читателем и убедиться, что форматирование сохранилось, а у читателя нет панели и элементов редактирования. Вставить из буфера форматированный текст с неподдерживаемыми тегами и убедиться после сохранения, что опасные атрибуты и теги не выводятся. Проверить мобильную компоновку с горизонтальным списком глав.
6. На экране соцсетей проверить возврат в хаб, назначить ответственного из участников проекта. Открыть план, проверить количество дней выбранного месяца и соответствие колонок рубрикам, затем создать публикацию: ответственный должен унаследоваться от соцсети. Выбрать другого исполнителя, сохранить, снова открыть карточку и проверить сохранённое переопределение; затем изменить и удалить публикацию.
7. Загрузить до четырёх изображений в поля «Референсы и скрины» и «Визуал», сохранить публикацию и проверить сжатые превью, встроенный просмотр по клику, закрытие просмотрщика по крестику и Escape, удаление изображения и цвет статуса в сетке.
8. Добавить комментарий к сохранённой публикации.
9. Открыть «Историю» и проверить появление действий создания и изменения публикации, изображения, референса, комментария, анализов и документов аудита и блокнота с правильным автором и временем. Убедиться, что изменение статуса, ответственного и роли показывает понятное описание, а читатель может открыть историю, но не записать или изменить событие напрямую.
10. Присоединить второго пользователя по коду.
11. Проверить интерфейс и фактические разрешения для `viewer` и `editor`: читатель видит сохранённого ответственного, но не получает список команды и не меняет назначения; редактор видит список и меняет ответственного соцсети и публикации, но не роли или состав команды. Если есть тестовый membership с устаревшей ролью `commenter`, открыть экран доступа владельцем и проверить его автоматический перевод в `viewer`.
12. Владелец вводит свободную функцию второго пользователя и проверяет её появление рядом с именем в списке исполнителей, затем меняет его роль и удаляет на экране доступа. Проверить исчезновение участника из списка назначений после повторного открытия экрана, сохранение снимка имени в старом назначении, запрет последующих операций с его открытой вкладки и отсутствие проекта после повторной загрузки этой вкладки. Убедиться, что удалить владельца через интерфейс нельзя.
13. Изменить название, площадки и рубрики проекта. Для рубрики без выбранной соцсети проверить цветную подсветку строки и перевод фокуса к ошибке. Быстро нажать сохранение несколько раз и убедиться, что создаётся только один документ, кнопка блокируется, а прогресс исчезает после ответа. Отдельно открыть старую рубрику без `networkIds`, проверить автоматический выбор существующих соцсетей и сохранение явной привязки.
14. С опубликованными актуальными функциями и `firestore.rules` проверить удаление тестового проекта владельцем и отсутствие связанных документов, включая `references`, `audienceAnalyses`, `competitorAnalyses`, `projectDocuments`, изображения и записи `activity`.
15. Проверить узкий экран и отсутствие критического горизонтального переполнения вне таблиц плана, анализа аудитории и анализа конкурентов.
16. Открыть `404.html` на широком и узком экране: проверить жест 6–7 у грустной оливки, появление второй оливки внутри нуля, движение её рук и ног, переход кнопки на корень сайта и статичное доступное состояние при `prefers-reduced-motion: reduce`.

Для небольших визуальных изменений достаточно релевантной части сценария. Изменения модели данных или правил требуют проверки минимум с владельцем и одной затронутой ролью.

## Обновление документации

Документация является частью готовности изменения. Перед завершением работы ответьте на вопросы:

- Изменилось пользовательское поведение или список возможностей? Обновите `README.md`.
- Изменилась навигация, интеграция или ответственность модулей? Обновите `ARCHITECTURE.md`.
- Изменились коллекции, поля, статусы, роли или Firestore rules? Обновите `DATA_MODEL.md`.
- Изменились запуск, проверка или выпуск? Обновите `DEVELOPMENT.md`.
- Появилось новое известное ограничение или устранено старое? Обновите README и соответствующий технический документ.

Если обновление не требуется, это должно быть осознанным выводом после проверки этих пунктов.

## Выпуск

1. Выполните релевантный дымовой сценарий.
2. Убедитесь, что документация соответствует изменению.
3. Опубликуйте новые версии Cloud Functions и Firestore rules, если соответствующие файлы менялись.
4. Опубликуйте статические файлы на хостинге.
5. Проверьте production-домен, авторизацию и один основной сценарий после публикации.

Изменение `firestore.rules` в репозитории само по себе не обновляет правила в Firebase Console.
